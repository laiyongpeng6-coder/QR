# 新功能开发流程

这份文档描述 UI 和功能如何串联。目标是让新功能从“想法”到“可交付页面”有固定顺序，避免 UI、状态、业务逻辑互相打架。

## 1. 适用范围

适用于所有新功能和重构：

- 新页面
- 新交互
- 新模块
- 现有页面的视觉重做
- 现有业务流程调整

## 2. 总原则

1. 先定义用户要做什么，再定义页面长什么样。
2. 先定义状态，再定义 UI。
3. 先做骨架，再做视觉细节。
4. 先保证可用，再保证好看。
5. 共享能力放 `core`，业务能力放 `feature`。

## 3. 推荐开发顺序

### 第 1 步：写清楚场景

先回答三个问题：

- 用户为什么要用这个功能？
- 用户什么时候会用？
- 用户完成后得到什么结果？

输出可以很短，但必须具体。

### 第 2 步：拆状态

先把页面会出现的状态列出来，例如：

- loading
- empty
- normal
- error
- success
- permission denied

如果状态没拆清楚，后面 UI 很容易返工。

### 第 3 步：定信息层级

页面上要明确：

- 主标题是什么
- 次要说明是什么
- 主要操作按钮是什么
- 辅助操作按钮是什么
- 哪些信息是“必须先看到”的

这一步决定页面是不是“乱”。

### 第 4 步：先做页面骨架

先只做结构，不追求漂亮：

- 顶部区域
- 内容区域
- 底部操作区
- 空状态 / 错误状态
- 弹窗 / Bottom Sheet

这个阶段的目标是“能走通流程”。

### 第 5 步：接 ViewModel

页面骨架稳定后，再把状态接进来：

- UI state
- event
- effect / one-shot action
- loading 和错误处理

建议一个页面只对应一个明确的状态模型。

### 第 6 步：接业务层

业务逻辑优先放在：

- `core/domain` 的 model / use case / repository interface
- `core/data` 的 repository implementation
- `feature/*/ViewModel` 的状态编排

不要把复杂业务塞进 Composable。

### 第 7 步：做视觉升级

当功能跑通后，再做视觉：

- 统一圆角
- 统一间距
- 统一按钮层级
- 统一颜色变量
- 增加插画 / 图标 / 渐变 / 层次
- 补转场动效

### 第 8 步：补测试

至少补一种：

- ViewModel 单元测试
- Composable UI 测试
- 仓库层测试
- 导航流程测试

## 4. 模块职责

### `app`

只放应用壳和导航编排：

- `MainActivity`
- `MainNavHost`
- `TabNavigation`
- 路由定义

### `core/domain`

只放领域约束：

- 数据模型
- 仓库接口
- 业务用例

### `core/data`

只放数据实现：

- Room
- Datastore
- Repository 实现
- 网络层将来也放这里或相邻基础模块

### `core/ui`

只放可复用 UI 能力：

- theme
- colors
- typography
- 通用按钮
- 通用卡片
- loading / empty / error 组件

### `feature/*`

每个 feature 只负责自己的页面、状态和局部组件。

## 5. UI 和功能怎么串联

推荐按照下面链路推进：

```text
用户场景
  -> 状态模型
  -> 页面骨架
  -> ViewModel
  -> 数据层 / 业务层
  -> 交互完善
  -> 视觉升级
  -> 测试
```

如果是从零做功能，最稳的做法是：

1. 先写 `Route`
2. 再写一个空壳 `Screen`
3. 再写 `UiState`
4. 再写 `ViewModel`
5. 再接 repository / use case
6. 再做动画和美化

## 6. 新 UI 的最小落地标准

如果是一个新页面，至少应该有：

- 标题
- 说明
- 主要操作按钮
- 次要操作按钮
- loading 状态
- error 状态
- empty 状态

如果是 onboarding 页面，至少应该有：

- 每页一个明确卖点
- 一个主视觉
- 一个主要按钮
- 一个跳过入口
- 清晰页码或进度提示

## 7. 重构时的边界

重构时优先级如下：

1. 不破坏现有功能
2. 不破坏导航
3. 不破坏数据持久化
4. 不破坏多语言资源
5. 不破坏可测试性

如果要改动共享组件，必须先确认是否会影响别的 feature。

## 8. AI 协作建议

让 AI 干活时，建议一次只给一个明确目标：

- “把这个页面重做得更有层次”
- “把这个状态模型拆出来”
- “把这个流程串成导航”
- “把这个组件抽到 core/ui”

不要一次要求它同时完成：

- 页面重构
- 业务逻辑重写
- 数据层改造
- 国际化
- 动画

那样最容易失控。

## 9. 交付检查清单

一个功能完成后，建议检查：

- 页面是否能从入口跑到结果
- loading / error / empty 是否可见
- 返回键是否正常
- 导航是否会重复入栈
- 文案是否已抽成资源
- 共享组件是否应该复用
- 是否需要补测试

## 10. 可复用模板

如果你要把这个流程直接发给 AI，可以用下面这个格式：

```text
目标：
现在状态：
允许修改的文件：
不能修改的文件：
UI 要求：
业务要求：
状态列表：
验收标准：
```

## 11. 当前项目建议

对 Fast QR Scan 来说，比较合适的开发顺序是：

1. 先把 onboarding 和主要 tab 的视觉统一起来。
2. 再把 scanner / generator / history 的空状态和错误状态统一起来。
3. 再做 ai-workspace 和 product-lookup 的高级交互。
4. 最后才做云端模板、订阅和广告。
